# Info·Safety 시설의 게임적 이득 — 후보안

- 작성일: 2026-08-11 / 코드 대조: 2026-09-03
- 상태: **방향 확정 + v0 범위 확정 (2026-08-11).**
  - **공통 방향**: NPC의 목적지로 만들지 않는다
  - **Safety = S-1(거리 기반 응급 해결 시간) 채택.** 스태프 파견 로직 소유자 확인이 선행
  - **Info = I-1(탐색 반경 확대) + I-3(미아·분실물 Event 억제)를 채택하되 v0 범위에서는 제외.**
    경제를 먼저 하고 P1에서 붙인다. **지금 이 문서에 설계를 남겨두는 것이 v0의 산출물이다** —
    나중에 다시 고민하지 않기 위해서다
- 배경: `Info`·`Safety`는 취향(`preference_vector`)도 Need 해소도 없어서 `BuildCandidates`가
  **의도적으로 후보에서 제외**한다(`utility_ai_todo.md` 6절, 2026-08-10). 그래서 지금은
  **UtilityAI의 자발적 목적지 선택에는 직접 효과가 없다**（아래 I-1/I-3/S-1 효과는 미구현. 시설 건설·비용·배치와 다른 모듈까지 효과가 전혀 없다는 뜻은 아님）.
- 관련: 기획서 §6.3(Event는 스태프 배치 후 NPC가 자동 수행), §8.1(Staff 6명 풀 — 2026-10-09 이후 코드 기본 스태프는 1명(`InitialStaffCount`), 나머지는 고용), AT-009(Ground 무페널티)

## 0. 확정된 방향 (2026-08-11)

**NPC가 자발적으로 찾아가는 목적지로 만들지 않는다.** 이유는 두 가지다.

1. 실제 축제에서도 안내소·의무실은 **필요가 생겼을 때만** 가는 곳이다. 취향으로 가는 곳이 아니다.
   Need를 새로 만들어(`need_information`) 목적지화하면 근거 없는 계수가 늘고, 화장실·식음료와
   같은 층에서 경쟁하게 되어 Utility 식이 부정확해진다.
2.  **Event는 플레이어가 스태프를 배치하고 NPC가 자동 수행**한다.
   Info·Safety는 그 **스태프 파견의 성능을 바꾸는 시설**로 두는 것이 기획서와 일치한다.

### 지켜야 하는 제약 2개

- **AT-009 (Ground 무페널티)**: "플레이어가 직접 가서 이득"은 **보너스만** 가능하다.
  직접 방문이 필수가 되면 Ground를 안 쓰는 플레이어가 손해를 본다 — 기획서 설계 원칙 위반이다.
- **소유 경계**: `Safety` 지표(0~100)의 소유자는 이정원 님이고 `UI_API.md`상 상태는 `❌ 없음`이다.
  `Info`는 대응 지표조차 없다. 아래 후보 중 지표를 건드리는 것은 전부 **합의 대상**이다.

### 1.1 채택안 — I-1 + I-3 (P1, v0 제외)

**2026-08-11 사용자 결정: 둘 다 채택하되 v0에서는 만들지 않는다.** 경제가 먼저다.
아래는 P1에 착수할 때 다시 고민하지 않기 위한 설계 기록이다.

#### I-1 탐색 반경 확대 — 상세

지금 `FFF_ZoneSystemBridge::BuildCandidates`의 일반 필터는 **현재 Zone + 직접 인접 Zone**이다（공연 중 Sunset은 별도 전역 예외）.
안내소 커버리지 안에 있는 Party는 이 필터를 완화한다.

```text
커버리지 밖  →  현재 Zone + 직접 인접 Zone (+ 공연 중 Sunset)
커버리지 안  →  현재 Zone + 직접 인접 Zone + 전역 인기 상위 K (제안, 미구현)
```

- 전역 인기 상위 K는 `utility_ai_todo.md` 2절의 **"후보 집합 전역 인기 상위 K 계수화"와 같은 작업**이다.
  둘을 따로 만들면 안 된다 — K가 두 곳에 생긴다
- 계수 2개 (둘 다 `assumption`): `info_coverage_candidate_bonus_k`, 그리고 커버리지 정의값
- **커버리지는 Zone 단위로 본다.** 반경(cm)으로 하면 시설마다 원을 그려 Zone 격자와 교차 판정을
  해야 한다. 밀집도 v0이 "시설 밀집도 ≈ Zone 밀집도"로 근사한 것과 같은 이유로 Zone 단위가 싸다
- **게임적 의미**: 안내소를 지으면 손님이 먼 구역까지 퍼진다 → 혼잡 분산 + 매출 분산.
  플레이어가 "왜 저 구석 부스에 손님이 없지?"를 해결하는 수단이 된다.
  리얼리즘이 아니라 **메커니즘**이다(신규성 선호를 넣은 것과 같은 이유)
- ⚠️ **민감도 분석과 얽힌다**: 상위 K는 부익부 피드백을 만든다. 안내소가 K를 키우면
  "안내소를 지었더니 인기 부스만 더 몰렸다"가 될 수 있다. 켤 때 분포를 같이 봐야 한다

#### I-3 미아·분실물 Event 억제 — 상세

`Info_LostFound` 커버리지가 해당 Event의 **발생 확률 또는 해결 시간**을 낮춘다.

- **선행 조건**: Event 종류 목록이 필요하다. 기획서 §9.2 "Event 처리" 토글 안에 있는 것으로
  보이는데 공개 페이지에서 펼쳐지지 않았다(2026-08-11 확인). 목록 없이는 어느 Event에
  걸리는지 정할 수 없다
- 소유 경계: Event 규칙의 제안 소유자는 `UFF_FestivalEventSubsystem`(김시리·백종태 공동)이다（해당 클래스는 현재 저장소에 없음）. **내 파트 안**이다
- 내 쪽 연결점: 미아 Event가 그룹 이탈로 이어지면 `Leave` 경로와 만난다.
  그때 **리더 퇴장 = 그룹 전체 퇴장** 규칙이 그대로 적용되는지 확인해야 한다

### 2.1 채택안 — S-1

（2026-09-03 코드 대조: 거리 기반 해결시간은 채택된 설계이나 실행 코드가 없다. Utility 후보용 FFF_WalkDistanceMatrix는 구현됐고 기본 꺼짐이지만 Safety 이벤트에 연결되지 않았다. 아래 “들어오면 정확해진다”는 미래 제안이며 자동 연동을 뜻하지 않는다.）

**시설의 위치가 의미를 갖는 유일한 자연스러운 방법**이고, "의무실을 어디에 둘까"라는 배치 판단을
플레이어에게 준다. 광훈님 `WorldLocation` 노출 커밋(`2c7766d`)으로 전제조건이 방금 풀렸다.

```text
Event 해결 시간 = 기본 처리 시간 + (가장 가까운 Safety 시설 → Event 지점 거리) / 스태프 이동 속도
Safety 시설이 없으면  →  출발점을 어디로 둘지 규칙이 필요하다 (아래 미결)
```

- **거리는 이미 계산 가능하다.** `FFFZSFacilityReadModel::WorldLocation`(cm) + Event 지점 위치.
  직선거리 근사이고, 실제 보행거리 행렬이 들어오면 정확해진다(`utility_ai_todo.md` 5절 대기 항목)
- **재사용**: `FFF_ZoneSystemBridge`가 이미 `DistanceMeters`를 만드는 코드를 갖고 있다.
  같은 환산을 두 번 구현하지 않는다
- 계수: 스태프 이동 속도. **`npc_walk_speed_mps`와 같은 값인지 별개인지 정해야 한다** —
  스태프는 뛸 수도 있다. 소유자는 crowdAI(이정원)

**미결 — 착수 전에 정할 것**

1. **스태프 파견 로직의 소유자가 누구인가.** Event 규칙은 `UFF_FestivalEventSubsystem`(김시리·백종태)인데,
   "스태프 NPC를 실제로 이동시키는 것"은 crowdAI다. 시간 계산만 내가 하고 이동은 그쪽인지,
   아니면 이동 없이 시간만 시뮬레이션하는지(P0에서는 후자가 훨씬 싸다)
2. **Safety 시설이 0개일 때의 출발점.** 맵 중앙? 입구? 이 값이 "안 지으면 얼마나 손해인가"를 정한다.
   근거 없는 상수가 되므로 `assumption`으로 명시한다
3. **S-2(혼잡 Critical 억제)는 v0에서 넣지 않는다** — 채택되지 않았다. 다만 Need→체류시간 드레인과
   같은 계수 축을 공유하도록 설계돼 있으니, 나중에 켤 때 드레인 배수에 항을 더하는 형태가 된다

## 3. 플레이어 직접 방문 (보너스 전용)

AT-009 때문에 **필수가 될 수 없다.** 보너스로만 둔다.

- `Safety_Security`에서 직접 순찰 → 짧은 인터랙션, 소액 Satisfaction 또는 Blue Diamond
- `Info_GeneralInfo`에서 직접 안내 → 같은 형태
- 둘 다 **스태프 파견으로도 100% 달성 가능**해야 하고, 직접 하면 더 빠르거나 소량 보너스가 붙는 정도
