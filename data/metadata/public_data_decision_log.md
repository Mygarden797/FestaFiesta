# 공공데이터 도입 결정 기록 — 2026-08-03

## 이번 단계의 결론

- 한국관광 데이터랩에서 사하구 관광지 13곳의 `성·연령 방문 집중률`은 확보했다.
- 같은 기간·같은 관광지 단위의 `관광지별 방문자 수`는 별도로 확보하지 못했다.
- 따라서 v0에서는 13개 관광지를 동일한 비중으로 취급한 기준분포를 사용한다.
- 이 결과는 사하구 전체 관광객 분포도, 실제 선택 효용계수도 아니다.
- NPC 아키타입 인구 비율로 직접 사용하지 않고 Utility AI의 선호도 사전값 후보로만 사용한다.

## 확정·가정·추후 검증

| 상태 | 내용 |
|---|---|
| 확정 | 원본에는 관광지 13곳과 성·연령 세그먼트 14개의 집중률이 있다. |
| 확정 | 산출표는 `13 × 14 = 182행`이며, 한 행은 `관광지 한 곳 × 성·연령 세그먼트 한 조합`이다. |
| 가정 | 관광지별 방문 규모를 알 수 없어 13개 관광지를 동일가중으로 평균했다. |
| 가정 | Utility AI에서는 `lambda_affinity × centered_log_share_ratio`로 연결하며, `lambda_affinity`는 민감도 실험용 노브다. |
| 추후 검증 | 데이터랩 집중률의 기준 모집단·통신사 추정 방식·표본 편향·이용조건을 확인한다. |
| 추후 검증 | 실제 방문 규모가 확보되면 동일가중 평균을 규모가중 평균 및 축소추정으로 교체한다. |

## 계산 방법

1. 각 성·연령 세그먼트에 대해 관광지 13곳의 집중률을 산술평균한다.
2. 관광지별 관측 집중률을 이 평균과 비교한다.
3. `log_share_ratio = ln(관측 집중률 / 동일가중 기준 집중률)`을 계산한다.
4. 관광지 안에서 14개 로그비의 평균을 빼 `centered_log_share_ratio`를 만든다.
5. 양수는 기준보다 상대적으로 많이 관측, 음수는 상대적으로 적게 관측됐다는 뜻이다.

```text
ResidentPopulationPrior (confirmed)
  → VisitorPropensityAssumption (실측 없음)
  → FestivalVisitorSyntheticPopulation (시나리오 산출물)
```

- 산출: `data/derived/visitor_population_prior_v0.csv` (28행 = 시나리오 2 × 세그먼트 14)
- `resident_neutral_v0`: 세그먼트별 방문 성향이 같다고 가정 → 방문객 구성 = 주민 구성

- 두 시나리오의 총변동거리 **TVD = 0.1144**. 이 값이 현재 방문객 구성에 대해 정직하게 말할 수 있는 불확실성 폭이다.

| 상태 | 내용 |

## 2026-08-05 갱신 — total_visitor_count 재산정 (20,000 → 950)

사용자 확인: 300~700은 성능 체크포인트이며 **700이 현재 단기 목표 동시 체류 NPC 수**(임의로 정한 값, 재조정 가능).

Little's Law로 역산: `동시 체류 = N × (S/T) / (피크·평균 비율)`
- `T`(Live 길이) = 240분(확정, 17:00~21:00)
- `S`(평균 체류) = 240 × 0.5 × 1.0667(stay_duration_multiplier 삼각분포 평균) ≈ 128분
- 피크·평균 비율 = 1.4(draft_assumption — 유입 곡선이 저녁 내내 평평하면 1.0, 공연 시간대로 뾰족하게 몰리면 2.0에 가까워진다. 지금은 그 사이 중간값으로 임시 고정)
- N(하루 기준) = 700 × (240/128) / 1.4 ≈ **950명/일**

| 상태 | 내용 |
|---|---|
| 확정 | `total_visitor_count`는 **하루 기준** 값이다(3일 총합 아님) — 시뮬레이션이 매일 인구를 새로 스폰하는 구조라 3일 누적치는 의미가 없다. |
| 변경 | 20,000 → 950, 범위 5,000~80,000 → 400~1,400(성능 체크포인트 300~1,000 동시 목표 대응). `status: assumption` 유지(피크·평균 비율이 draft_assumption이라 최종 확정은 아님). |
| 미해결 | 피크·평균 비율(1.4)은 실제 유입 곡선 설계가 나오기 전 임시값이다. 유입이 공연 시간대로 몰릴수록(뾰족한 곡선) 비율이 커지고, 그만큼 N은 작아져야 한다. 수요 생성 곡선(파이프라인 문서 §6.1) 설계 시 재계산 필요. |
| 방향 제시 | 동시 체류 목표(700) 자체를 올릴지는 "판단 에이전트 수"와 "이동·존재 에이전트 수"를 분리해서 실측한 뒤 결정 — 아래 근거로 Utility AI 판단 비용은 병목이 아닐 가능성이 높다. `DecisionBudgetPerTick=32`, `reevaluate_interval_seconds=120` 기준 이론적 판단 처리량(30Hz 틱 가정) = 32×30=960건/초, 이걸로 감당 가능한 인구 상한 = 960×120=115,200명 — 700보다 훨씬 크다. 즉 지금 병목이라면 판단(Utility AI)이 아니라 이동(NavMesh·회피)·렌더링 쪽일 가능성이 높고, 이건 이정원 님 쪽 실측이 먼저 필요하다. |
