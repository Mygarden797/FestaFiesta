기준: 기존 100종 후보에서 역할·외형의 중복과 제작·연동 부담을 고려해 70종을 선별했다. 선정 시설의 이름·분류·제작 강조점을 유지하고 번호는 1–70으로 다시 매겼다.

## 2. 제작할 때 가장 강조할 점

### 형태와 분위기

1. **멀리서도 시설 종류가 구분되어야 한다.** 지붕, 간판, 카운터, 대표 소품 중 하나를 크게 강조한다. 작은 글씨를 읽어야 정체를 알 수 있는 모델은 피한다.
2. **위에서 보는 운영 화면과 가까이 걷는 화면을 함께 고려한다.** 지붕만 보아도 분류가 드러나게 하고, 전면에서는 출입구·이용 위치가 자연스럽게 읽히도록 한다.
3. **해안 축제의 통일감을 유지한다.** 청록·짙은 청록·크림·목재·따뜻한 발광색을 공통 기반으로 삼고, 품목별 강조색을 더한다. 기존 대표 메시·재질과 게임 화면에서 비교한다.
4. **단순한 형태와 재질 차이로 표현한다.** 목재, 천, 금속, 유리의 차이는 큰 면·거칠기·색으로 먼저 만든다. 나사·음식 알갱이·천 섬유까지 전부 입체화하지 않는다.
5. **고객 전면을 명확히 한다.** 판매 창구, 무대 관람 방향, 사진 촬영 위치, 화장실 출입구가 서로 혼동되지 않게 한다.
6. **재사용할 부품을 먼저 만든다.** 천막, 카운터, 바퀴, 간판 프레임, 의자, 울타리, 조명 갓을 공유한다. 원본은 부품별로 편집 가능하게 보관하고 정적 출력본에서 필요한 부분만 합친다.
7. **낮에도 형태가 성립해야 한다.** 조명 시설을 포함해 발광을 껐을 때도 구조가 읽히게 한다. 야간 밝기로 형태나 재질 결함을 가리지 않는다.

### 치수·원점·전면 방향

| 항목 | 제작 기준 |
|---|---|
| 실제 크기의 기준 | 시설 PDA의 현재 `FootprintSizeCells`, `PlacementObstacleHeightCm`, `VisualSizingMode`를 확인한다. 새 시설은 이 값을 정한 뒤 블록아웃한다. |
| 이 프로젝트의 셀 | **1 Cell = 1cm**다. 이름에 Cells가 있어도 100cm 격자로 해석하지 않는다. 예: 폭 6m·깊이 3m는 `(600, 300)`이다. |
| Blender 단위 | 일반 시설 제작기는 `METRIC`, `scale_length=1.0`으로 미터를 사용한다. 6m 폭은 Blender에서 6으로 제작한다. |
| 언리얼 단위 | 센티미터 기준으로 이관한다. 같은 모델이 600cm인지 확인하고 배치 테스트의 Actor Scale은 `(1,1,1)`로 시작한다. |
| 일반 시설 원점 | 바닥 영역의 중앙, 지면 높이 Z=0. 전면은 시설 로컬 **+Y**, 위는 **+Z**다. |
| Road·Tile 예외 | 기존 바닥 원본은 바닥 중앙 원점·진행 **+X**, 원본 규격 400×400×8cm다. 실제 설치 크기·높이는 각 PDA의 현재 값을 따른다. 일반 시설의 +Y 전면 규칙을 그대로 덮어씌우지 않는다. |
| Transform | 출력용 사본에서 불필요한 회전·스케일을 정리하고 음수 스케일·뒤집힌 면을 확인한다. 원점과 지면 기준이 유지되는지 다시 검사한다. |
| 배치 경계 맞춤 | 프로덕션 시설은 기존 Spec이 권장하는 정확 맞춤 방식을 검토한다. 정확 맞춤에서는 `VisualOffsetCm=0`이고 `VisualRotation`은 허용된 직각 Yaw 범위여야 한다. 원본 비율부터 목표 치수에 맞춰 과도한 자동 늘어남을 피한다. |
| 이용 지점 | 고객이 설 위치·앉을 위치·입구·출구를 작업 가이드로 표시한다. Blender Empty를 만들었다고 PDA Anchor로 자동 등록되는 것은 아니다. |

**좌표계를 혼합하지 않는다.** 시설 `Anchors`는 건물 중심 기준 로컬 cm 좌표이고, `QueueReservedRects`는 회전 전 footprint 왼쪽 아래 기준 1cm 셀 좌표다. Blender의 미터 좌표를 복사할 때 단위와 원점을 모두 변환해야 한다. 대기열 예약 면적을 늘리는 것만으로 실제 정원이나 대기 슬롯이 늘지는 않는다.

### 충돌·재질·연출 분리

- 시각 메시, 단순 충돌, 제작 가이드, 실제 광원·효과를 구분해 관리한다. 간판 조명·영상 화면·물 표면처럼 따로 제어할 면은 재질 슬롯이나 별도 부품으로 남긴다.
- UCX는 `UCX_<RenderMeshName>_00`, `_01`처럼 렌더 메시 이름에 맞춘 닫힌 볼록 충돌체로 제작한다. 문·아치·족욕 공간 전체를 큰 박스 하나로 막지 않는다. 복잡한 빈 공간은 여러 단순 충돌체로 나눠 확인한다. [Epic FBX Static Mesh 안내](https://dev.epicgames.com/documentation/en-us/unreal-engine/fbx-static-mesh-pipeline-in-unreal-engine)
- **플레이어 충돌과 NPC·배치 규칙은 별개다.** 현재 시설은 메시의 기존 충돌을 플레이어 이동에 재사용하지만, NPC 이동·배치 경계는 시설 Spec과 관련 시스템을 따른다. 통과 가능한 메시를 만들었다는 이유만으로 NPC가 내부를 통과한다고 가정하지 않는다.
- UV0에는 표면 재질·간판을 정리한다. 제작 방식에 맞춰 UV1·라이트맵도 확인하고, 자동 생성만으로 결과를 확정하지 않는다. 삼각화 뒤 천막·곡면·큰 다각형의 음영을 검사한다.
- Blender의 복잡한 노드·절차형 재질·컴포지터 결과가 그대로 이관된다고 가정하지 않는다. 필요한 표면 정보를 텍스처로 굽거나 언리얼 재질로 재구성한다. FBX 재질 전송에는 지원 범위가 있다. [Epic FBX Material 안내 — UE 5.7](https://dev.epicgames.com/documentation/en-us/unreal-engine/fbx-material-pipeline-in-unreal-engine?application_version=5.7)
- 연기·분무·물결·영상·음악·센서 반응·게임 점수는 모델과 별도 작업이다. 모델에는 위치와 부착 기준을 마련하고, 필요한 언리얼 연출과 동작을 작업 기록에 적는다.
- 움직일 문·발판·바퀴·촬영 장치는 정적 본체와 별도 출력한다. 현재 일반 시설 FBX 임포터는 `combine_meshes=True`, 정적 메시 임포트, 애니메이션 출력 없음이므로 가동 부품을 같은 출력물에 넣고 자동 분리를 기대하지 않는다.

## 3. Blender MCP 작업 순서

이 순서는 앞으로 적용할 제작 절차다. 여기 적힌 단계가 실행되었다는 뜻은 아니다.

1. **연결과 원본 확인:** Blender MCP의 파일 경로·데이터블록 요약 도구로 열린 파일과 기존 오브젝트를 확인한다. Blender 버전과 사용 가능한 내보내기 API를 확인하고 기존 작업 파일을 별도 저장한다.
2. **시설 하나의 작업 범위를 지정:** `FAC_<FacilityDefinitionId>` 컬렉션 아래에 `VIS`, `COL`, `GUIDES`를 구분한다. 광원·효과 위치 가이드는 별도 관리한다. 이는 제안하는 Blender 작업 규칙이며 자동 임포트 규약은 아니다.
3. **블록아웃:** PDA 목표 치수, 바닥 중앙 원점, 전면 방향, 고객 접근면을 먼저 맞춘다. 캐릭터 크기 비교용 가이드를 두고 큰 형태만 만든다.
4. **대표 1종 왕복 확인:** 상세 모델링 전에 FBX 한 개를 내보내 언리얼에서 치수·방향·원점·재질 슬롯·충돌을 확인한다. 도로·조명처럼 경로가 다른 유형은 각각 대표 샘플을 확인한다.
5. **단계별 제작:** 큰 실루엣 → 기능을 보여 주는 부품 → 재질 → 필요한 세부 순서로 진행한다. MCP 코드 실행을 시설 단위·공정 단위로 나누고, 각 단계 뒤 오브젝트 요약과 화면 캡처로 결과를 확인한다.
6. **재실행 가능한 스크립트:** 오브젝트 이름과 대상 컬렉션을 고정한다. 재실행 시 `.001` 복제물이 쌓이지 않도록 대상만 갱신하고, 다른 시설 컬렉션이나 장면 전체를 일괄 삭제하지 않는다.
7. **검사와 저장:** 치수, Transform, 재질 슬롯, UV, 면 방향, 충돌 이름을 기록하고 `.blend` 원본·제작 스크립트를 저장한다. Blender 미리보기와 언리얼 화면을 별도로 남긴다.
8. **이관·등록·검증:** FBX 임포트 뒤 PDA 연결, 카탈로그 이미지, 가격·수익·조합 등의 별도 데이터 등록 상태를 확인한다. 실제 시설 배치와 플레이까지 통과한 상태를 최종 완료로 기록한다.

MCP에서는 연결된 서버의 파일/오브젝트 요약, Python 실행, 뷰포트 캡처 도구를 사용한다. 노출된 도구 이름과 인자는 실행 시 실제 도구 스키마를 따르며, 존재하지 않는 API나 메뉴를 추측해 사용하지 않는다.

### 현재 절차형 파이프라인과 신규 MCP 원본의 차이

현재 도구는 `Saved/FacilityDefinitionAuthoringManifest.json`과 `Saved/FacilityMeshBuildManifest.json`을 검증하고, 명시적으로 절차형 도구에 관리 권한을 준 메시만 처리한다. 소유권 플래그·메타데이터·경로·등록된 builder·해시 조건이 있으며, 70개 신규 모델을 폴더에 넣는 것만으로 자동 등록되지 않는다.

임포트 시 선택된 관리 대상 전체 집합, 현재 PDA에서 생성한 digest, FBX의 SHA256이 일치해야 한다. MCP에서 FBX를 수정한 뒤 이전 build manifest를 그대로 재사용할 수 없다.

- 크기의 원본은 PDA다. authoring manifest는 `authoritative=false`인 파생 파일이며, 값을 손으로 고쳐 사양을 바꾸지 않는다. PDA가 바뀌면 다시 생성한다.
- 기존 일반 생성기의 FBX 출력은 `SourceAssets/Zone/FacilityMeshes`, 관리 메시 루트는 `/Game/FestaFiesta/Zone/Test_Asset/Asset`다. 이 경로와 관리 플래그를 신규 아티스트 모델에 무조건 적용하지 않는다.
- MCP로 손질한 모델은 **별도 원본과 명시적인 새 대상 경로로 임포트하는 방식을 우선 제안**한다. 기존 절차형 경로를 사용하려면 builder·소유권·manifest 생성·검증을 해당 모델에 맞게 먼저 준비한다.
- 기존 검증 스크립트 통과가 70종 전체의 검증을 뜻하지 않는다. `verify_facility_meshes.py`는 절차형 관리 대표 메시용 프로파일이다. 신규 시설은 실제 대상 목록과 PDA Data Validation, 게임 배치 검사를 함께 확인한다.
- 기존 일반 임포트·재질 수정 도구는 `UnrealEditor-Cmd -run=pythonscript -unattended` 실행을 요구한다. 열린 에디터의 MCP Python 실행창에서 이 수정 스크립트를 직접 실행하지 않는다. 실제 실행에는 프로젝트·스크립트 경로를 포함한 완전한 명령을 준비한다.
- Road/Tile·조명은 별도 도구와 가이드가 있다. 일반 생성기와 동일한 축·LOD·썸네일 설정을 일괄 적용하지 않는다.

## 6. 파일·이름·납품 구성 제안

시설 ID는 `대분류_소분류_고유이름`을 사용한다. 고유이름은 의미 있는 영문 PascalCase로 정하고 등록 전에 기존 ID와 중복을 확인한다. 아래 이름과 경로는 **신규 작업용 예시이며 아직 생성되거나 등록되지 않았다.**

（10/14 기준: 시설 ID·PDA·`SM_FF_` 이름은 이 규칙대로 등록되었다. 실제 언리얼 아트 경로는 제안한 `/Game/FestaFiesta/Art/...`가 아니라 `/Game/Asset/FacilitiesAsset_HKH/FacilityExpansion70/<대분류>/<고유이름>`이고, 저장소의 제작 원본은 `Design/SourceArt/FacilityExpansion70`에 있다.）

| 항목 | 예시 |
|---|---|
| 시설 ID | `Booth_FoodStall_CafeTruck` |
| 표시 이름 | `카페 트럭` |
| PDA | `PDA_FFZS_Booth_FoodStall_CafeTruck` |
| 정적 본체 | `SM_FF_Booth_FoodStall_CafeTruck` |
| 충돌 | `UCX_SM_FF_Booth_FoodStall_CafeTruck_00` |
| 신규 원본 폴더 제안 | `SourceArt/FacilityExpansion70/Booth/Booth_FoodStall_CafeTruck/` |
| 신규 언리얼 아트 경로 제안 | `/Game/FestaFiesta/Art/FacilityExpansion70/Booth/CafeTruck` |
| 시설 정의 경로 | 기존 대분류 체계인 `/Game/FestaFiesta/Building/FF_Data_Building/Booth` 아래에 등록 검토 |

시설 하나의 납품에는 다음을 포함한다.

- 편집 가능한 `.blend` 원본과 재실행 가능한 MCP/Python 제작 스크립트.
- 본체 FBX·UCX, 필요한 가동 부품의 개별 출력 파일.
- 사용한 텍스처 원본·출력본, 재질 슬롯 이름과 연결 설명. 외부 이미지 경로 누락도 확인한다.
- 실제 치수(cm), 전면 방향, 피벗, 메시 bounds, 삼각형 수, 재질 슬롯 수, 충돌체 수, LOD 구성 기록.
- 정면·후면·상부·게임과 유사한 사선 뷰, 주간·야간 확인 이미지.
- 카탈로그 썸네일. 기존 조명 가이드의 1024×1024 RGBA·투명 배경·직교 구도는 참고하되 대상 카탈로그의 기존 자산과 맞춘다.
- 추가 연결이 필요한 광원·화면·물·연기·음향·애니메이션·상호작용 목록과 위치 가이드.
- 언리얼 대상 경로, PDA 연결 상태, 실행한 검사의 결과와 남은 문제.

## 7. 제작 완료 판단 기준

### 시설마다 확인

- [ ] 70종 목록의 번호·이름·분류가 작업 기록과 일치한다.
- [ ] 큰 실루엣만 보아도 시설 종류가 구분된다.
- [ ] PDA 목표 크기, 원점, 전면, 지면 높이가 맞는다.
- [ ] 출력용 메시의 음수 스케일·뒤집힌 면·삼각화 음영·겹친 면을 확인했다.
- [ ] 재질 슬롯·UV·텍스처가 누락 없이 연결되며 Blender 전용 노드에만 의존하지 않는다.
- [ ] 움직일 부품·화면·발광·물 표면 등 독립 제어 대상이 구분되어 있다.
- [ ] UCX가 보이지 않는 벽으로 출입구·촬영 자리·족욕 공간을 막지 않는다.
- [ ] 언리얼에 가져온 뒤 크기·축·피벗을 Blender 기록과 비교했다.
- [ ] 시설 카탈로그에서 썸네일과 이름이 맞고 설치 미리보기가 정상이다.
- [ ] 회전·배치·이동·철거·저장/불러오기에서 시각 메시와 관련 기능이 함께 동작한다.
- [ ] 고객 이용 시설의 서비스 지점·대기열·NPC 접근과 플레이어 충돌을 각각 확인했다.
- [ ] Road/Tile은 연속 배치, 경계 접합, 회전, 단차, 상부 시설 정책을 확인했다.
- [ ] 조명은 켜기·끄기·밝기·색 변경·저장 복원에서 실제 광원과 발광 표면을 함께 확인했다.
- [ ] 제작한 기능과 아직 연결하지 않은 기능을 분명히 기록했다.

### 여러 시설을 함께 배치해 확인

70개를 모두 고밀도로 만드는 대신 **소형 부스·대형 무대·반투명 포토존·조명·바닥의 대표 샘플**을 먼저 배치해 비용을 측정한다. 삼각형 수만 보지 말고 재질 슬롯, 실제 광원, 그림자, 투명 면 겹침, 텍스처 메모리, 충돌 복잡도, 화면에 동시에 보이는 개수를 함께 본다.

구체적인 삼각형 수·텍스처 해상도·광원 수 상한은 이 문서에서 확정하지 않는다. 실제 게임 카메라와 목표 하드웨어에서 대표 장면을 측정한 뒤 제작 예산을 정한다. LOD 전환에서는 시설을 구별하는 간판·지붕·대표 소품을 먼저 보존한다.
