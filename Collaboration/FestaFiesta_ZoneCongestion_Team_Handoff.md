# 손님이 혼잡을 피하게 만들기 — 1단계 완료 보고 및 협의 요청

> 작성일: 2026-09-04
> 작성자: 한광훈 (FF_ZoneSystem)
> 읽는 사람: 이정원(Crowd), 김시리(Utility AI), 강민서(시간), 백종태(UI)
> 중요한 전제: **팀원 소유 파일은 한 줄도 수정하지 않았다.** 이번 작업은 전부 FF_ZoneSystem 플러그인과 Zone 브리지 폴더 안에서 끝냈고, 다른 담당 영역에 필요한 일은 이 문서로만 요청한다.

## 1. 30초 요약

우리 게임의 손님(NPC)은 "어디로 갈지" 정할 때 여섯 가지를 본다. **거리, 대기시간, 취향, 욕구, 매력도, 그리고 혼잡도.**

이 중 **혼잡도만 계속 0이었다.** 각 구역에 몇 명이 있는지 세어서 알려주는 코드가 아무 데도 없었기 때문이다. 손님 입장에서는 "사람이 아무리 많아도 그 사실을 모르는 상태"였다.

이번에 **세어서 알려주는 부분을 만들었다.** 이제 시스템은 구역별 인원을 1초마다 정확히 알고 있다.

다만 **아직 손님 행동은 눈에 띄게 바뀌지 않는다.** 세어봤더니 우리 축제장이 너무 넓어서, 계산상 "혼잡"이 성립하지 않기 때문이다(3절). 그 숫자를 어떻게 맞출지가 이번 회의의 핵심 안건이다.

| 단계 | 내용 | 상태 |
|---|---|---|
| 1단계 | 구역별 인원을 세어 시스템에 전달한다 | **완료 (이번 작업)** |
| 2단계 | 혼잡하면 손님이 다른 구역으로 옮기게 한다 | 정원·시리 님 협조 필요 |
| 3단계 | "몇 명부터 혼잡인가" 기준을 실제 규모에 맞춘다 | 회의에서 결정 필요 |

## 2. 무엇이 문제였고, 무엇을 만들었는가

### 비유

축제장을 30개 구역으로 나눠 놓고, 각 구역에 **"지금 여기 몇 명 있어요"라고 알려주는 안내원**을 두기로 설계했다. 안내원이 서 있을 자리(기능)는 만들어져 있었는데, **정작 아무도 그 자리에 배치되지 않았다.**

그래서 시스템은 모든 구역을 항상 "0명"으로 알고 있었다. 손님은 텅 빈 구역과 발 디딜 틈 없는 구역을 똑같이 취급했다.

### 이번에 한 일

그 **안내원을 배치했다.**

- 1초에 한 번, 손님 전원의 위치를 읽어서 어느 구역에 있는지 센다.
- 사람이 0명인 구역도 반드시 "0명"이라고 보고한다. (안 그러면 사람이 다 빠져나간 구역이 계속 "붐빔"으로 남는다 — 실제로 그렇게 되는 구조였다.)
- 축제 진행 속도를 2배속으로 돌려도 "5초 동안 붐볐다" 같은 판정이 어긋나지 않게, 시계를 게임 시뮬레이션 시계에 맞췄다.

### 손댄 파일

전부 작성자 소유 영역이다. 다른 사람 작업과 충돌하지 않는다.

| 파일 | 내용 |
|---|---|
| `Plugins/FF_ZoneSystem/.../FF_FFZSWorldSubsystem.h/.cpp` | 인원 보고 함수가 "받았다/못 받았다"를 알려주도록 수정. 등록된 구역 목록을 싸게 얻는 함수 추가 |
| `Source/FestaFiesta/Public/Zone/FF_ZonePopulationBridgeSubsystem.h` (신규) | 인원 집계 담당의 설계와 계약 |
| `Source/FestaFiesta/Private/Zone/FF_ZonePopulationBridgeSubsystem.cpp` (신규) | 실제 집계·보고와 확인용 콘솔 명령 |
| `Source/FestaFiesta/Private/Zone/FF_ZonePopulationBridgeTests.cpp` (신규) | 자동 검사 4종 |

## 3. ⚠️ 지금 이대로는 손님 행동이 안 바뀐다 — 회의 1순위 안건

세어보니 숫자가 이렇다.

| 항목 | 값 |
|---|---|
| 구역 하나의 크기 | 100m × 100m = **10,000㎡** |
| "쾌적하게 있을 수 있는 1인당 면적" 설정값 | 4㎡ |
| → 구역 하나의 **정원** | **2,500명** |
| 축제 전체 방문객 수 | **500명** |
| 구역 하나당 평균 인원 | 약 17명 |
| → 혼잡도 | 2,500명 중 17명 = **0.7%** |
| 손님이 "붐비네"라고 느끼기 시작하는 기준 | 정원의 80% = **2,000명** |

**500명이 한 구역에 전부 몰려도 20%다.** 기준선의 4분의 1이다.

이건 코드 버그가 아니다. 시스템은 정확하게 계산하고 있고, **"30만㎡ 부지에 500명은 실제로 안 붐빈다"고 올바르게 답하고 있다.** 축구장 40개 넓이에 500명이 흩어져 있는 상태다.

그래서 혼잡을 게임에서 체감시키려면 셋 중 하나를 골라야 한다.

| 선택지 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 실제 걸어 다니는 면적만 정원 계산에 쓴다** (추천) | 구역 100m×100m 중 실제 부스 앞 광장이 20m×20m라면 그 면적만 쓴다 → 정원 100명 | 숫자의 의미가 왜곡되지 않는다. 그런 용도로 만들어 둔 설정 칸이 이미 있다 | 구역마다 실제 광장 크기를 재서 입력해야 한다 (레벨 파일 편집 필요) |
| B. 방문객 수를 늘린다 | 500명 → 수천 명 | 가장 자연스럽다 | 성능 확인이 필요하고 다른 시스템에 영향이 크다 |
| C. 정원 숫자를 임의로 낮춘다 | 구역 정원을 2,500 → 50으로 손으로 지정 | 가장 빠르다 | 준비 화면의 "정원 대비 예상 방문객" 표시도 같이 바뀐다. 근거 없는 숫자가 남는다 |

**추천은 A다.** 다만 A는 강민서 님이 관리하는 레벨 파일을 열어야 해서 작업 시간 조율이 필요하다(5절).

## 4. 확인하는 방법 (누구나 따라 할 수 있음)

에디터에서 플레이(PIE)를 켜고, 물결표(`~`) 키를 눌러 콘솔 창을 연 다음 아래를 입력한다.

```
FF.Zone.Population
```

이렇게 나온다.

```
=== Zone 인구 === cycle=42 simTime=42.0s delta=1.00s 활성=500 존밖=13 보고=30 거부=0 주기=1.00s
Zone=GZ_TestMain_1     pop=  17 cap= 2500 ratio=0.007 state=Normal   area=10000m2
Zone=GZ_TestMain_2     pop=  34 cap= 2500 ratio=0.014 state=Normal   area=10000m2
...
```

읽는 법:

- `pop` — 지금 그 구역에 있는 사람 수. **이 숫자가 0이 아니면 1단계는 성공한 것이다.**
- `cap` — 그 구역의 정원
- `ratio` — 혼잡도 (pop ÷ cap). 0.8을 넘겨야 손님이 "붐빈다"고 느낀다
- `state` — Normal(평온) / Caution(주의) / Warning(경고) / Critical(위험)
- `활성` / `존밖` — 전체 손님 수와, 어느 구역에도 속하지 않은 손님 수

관련 명령:

| 명령 | 용도 |
|---|---|
| `FF.Zone.Population now` | 1초를 기다리지 않고 즉시 다시 센다 |
| `FF.Zone.PopulationReporting 0` | 이 기능을 완전히 끈다. **문제가 생기면 이걸로 원래 상태로 되돌릴 수 있다** |
| `FF.Zone.PopulationIntervalSeconds 2` | 몇 초마다 셀지 바꾼다 (기본 1초) |

## 5. 팀원께 드리는 요청

작성자가 대신 고칠 수 없거나, 고쳐서는 안 되는 부분이다.

| 누구에게 | 무엇을 부탁하는가 | 플레이어에게 왜 필요한가 | 우선순위 |
|---|---|---|---|
| **이정원 — Crowd** | 인원을 몇 초마다 세는 것이 적절한지 확정 (현재 1초) | 너무 드물면 혼잡 판정이 늦고, 너무 잦으면 성능을 먹는다 | 높음 |
| **이정원 — Crowd** | 손님 개인차(붐비는 걸 잘 참는 사람 / 못 참는 사람)를 결정 시점에 전달 | 지금은 전원이 똑같은 기준으로 판단해서 다 같이 움직인다 | 높음 |
| **이정원 — Crowd** | 시뮬레이션 시계가 배속에 따라 빨라지는 게 맞는지 확인 | 2배속에서 "5초 동안 붐볐다" 판정 기준이 달라진다 | 중간 |
| **김시리 — Utility AI** | 혼잡도를 실제로 읽도록 결정 코드의 고정값 한 줄 교체 (작성자가 만들어 리뷰 요청 가능) | 이게 없으면 세어봐야 손님이 안 본다 | 높음 |
| **김시리 — Utility AI** | 혼잡 가중치 조정은 3절 결정 이후에 | 기준이 틀린 상태에서 가중치를 만지면 원인을 못 찾는다 | 3절 이후 |
| **강민서 — 시간** | 3절 A안 선택 시, Test_Main 레벨 편집 시간 조율 | 레벨 파일은 두 사람이 동시에 못 고친다 | 3절 이후 |
| **백종태 — UI** | (통보) 3절에서 정원 숫자가 바뀌면 준비 화면의 "정원 N명 대비 최대 예상 M명" 표시가 함께 바뀐다 | 코드 수정은 필요 없다 | 낮음 |

## 6. 회의에서 결정할 것

1. **3절의 A / B / C 중 무엇으로 갈 것인가.** (추천: A — 실제 걸어 다니는 면적만 정원에 반영)
2. **인원을 몇 초마다 셀 것인가.** (제안: 1초. 혼잡 판정이 5초·3초 유지 기준이라 그보다 짧아야 한다)
3. **"혼잡하면 다른 구역으로 이동"을 이번 스프린트에 넣을 것인가.** 현재는 판단만 하고 실제 이동은 제자리 배회로 처리된다. 실제 이동은 Crowd 쪽 추가 작업이다.
