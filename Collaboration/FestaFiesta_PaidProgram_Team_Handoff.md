아직 남은 것은 예약 정보를 실제 손님 행동에 연결하는 일, 기존의 다른 구매 화면도 같은 규칙을 쓰게 하는 일, 기존 저장 과정의 알림 안전성을 높이는 일이다. 담당 코드에는 각 담당자의 기존 설계와 테스트가 있으므로 현재 작업자가 대신 수정하지 않았다.

| 누구에게 | 무엇을 부탁하는가 | 플레이어에게 왜 필요한가 | 우선순위 |
|---|---|---|---|
| 김시리 — Crowd/NPC | 예약 프로그램 손님을 실제로 만들고 해당 시설로 이동 | 돈을 낸 프로그램에 실제 참가자가 와야 함 | 높음 |
| 김시리 — Economy/NPC | 구매·예약·편성 저장을 중간 노출 없이 마무리 | 드문 재호출 상황에서도 이중 차감/반쪽 저장 방지 | 높음 |
| 김시리 — NPC | 같은 시설의 겹치는 예약을 저장소에서도 거절 | 다른 화면이 안전 검사를 우회해도 충돌 방지 | 중간 |
| 김시리 — Festival | 기획 데이터 검사를 Validate Assets 메뉴에 연결 | 기획자가 잘못된 값을 저장할 때 즉시 확인 | 중간 |
| 백종태 — PrepHUD/ViewModel | 기존 Program 탭도 새 안전 명령을 사용 | 어느 화면에서 구매해도 같은 규칙 적용 | 높음 |
| 백종태 — PrepHUD | 필요하면 시설 전용 피커를 기존 Program 탭과 통합 | UI를 하나로 운영하고 싶을 때 선택 | 선택 |

## 2. 지금 완료된 것과 아직 아닌 것

### 지금 완료된 것

- 시설을 클릭하면 정보 패널에서 유료 프로그램 상태를 볼 수 있다.
- 해당 시설에서 가능한 프로그램 목록을 열 수 있다.
- 카드 선택과 실제 결제가 분리되어 있다.
- 결제 직전에 단계, 시설, Gold, Staff, 중복, 시간 충돌을 다시 검사한다.
- 편성된 시설은 당일 이동·철거할 수 없다.
- 기획자는 Festival DataAsset의 `ProgramCatalog` 값만 바꿔 프로그램을 조정할 수 있다.
- 디자이너는 Facility/Picker/Card WBP에서 화면을 수정할 수 있다.

### 아직 담당자 연결이 필요한 것

- 구매 프로그램의 예약 손님이 실제 플레이에서 등장하고 시설을 방문하는 흐름
- 참가비를 어떤 조건에서 확정할지에 대한 기획 결정과 Crowd 연결
- 구매 처리 중 외부 알림이 들어와도 반쪽 상태가 보이지 않는 저장 순서
- 예약 저장소 자체의 시간 중복 최종 방어
- 기존 PrepHUD Program 탭의 공통 안전 명령 사용
- 기획 데이터 검사의 표준 **Validate Assets** 연결

## 3. 김시리님께 요청할 내용

### 요청 1 — 프로그램 예약 손님을 실제 게임 손님으로 연결

**쉽게 말하면**  
프로그램을 구매하면 “몇 명이 어느 시설에 몇 시에 올지”라는 예약표는 생긴다. 이제 Crowd 시스템이 그 예약표를 읽고 실제 손님을 만들고, 약속한 시설로 보내야 한다.

**왜 필요한가**  
이 연결이 없으면 구매와 예약 기록은 성공해도 플레이 화면에서 프로그램 참가자가 실제로 나타나지 않는다.

**부탁할 작업**

1. Live 손님 명단을 만들 때 프로그램 예약 인원을 일반 손님과 별도로 추가해 주세요.
2. 한 팀의 인원을 전부 만들 수 있을 때만 그 팀을 생성해 주세요. 자리가 부족하면 반쪽 팀을 만들지 않습니다.
3. 한 팀 전체가 생성된 뒤에만 예약 확정 API를 호출해 주세요.
4. 예약 손님의 목적지는 예약에 적힌 시설 고유 번호로 고정해 주세요.
5. 시작·종료 시간 동안 목적지 재선택과 조기 퇴장을 어떻게 막을지 기존 Crowd 규칙에 연결해 주세요.
6. 현재 기준은 “생성이 확정된 인원”을 프로그램 시작 때 정산하는 방식입니다. 이를 시설 도착 또는 서비스 시작 기준으로 바꿀지는 기획과 합의한 뒤 연결해 주세요.

**완료 확인**

- [ ] 프로그램을 사지 않은 날과 비교해 예약 인원만큼 손님 요청이 추가된다.
- [ ] 예약 손님이 정확한 시설로 이동하고 프로그램 종료 뒤 이동 제한이 풀린다.
- [ ] NPC 자리가 한 명이라도 부족하면 일행 일부만 만들거나 예약을 확정하지 않는다.
- [ ] 시설이 없어지거나 날짜가 바뀌면 예약·이동·잠금 상태가 남지 않는다.
- [ ] 합의한 참가 조건을 충족한 인원만 참가비에 반영된다.

**개발자 참고 위치**

- `UFF_ProgramReservationSubsystem::GetReservedPartyRequests`
- `UFF_ProgramReservationSubsystem::ConfirmReservedParty`
- `FF_CrowdSimulationSubsystem.cpp`와 Crowd 목적지/이동 계층

### 요청 2 — 구매 도중 외부 알림이 들어와도 한 덩어리로 저장

**쉽게 말하면**  
Gold 차감, 시설 시간 예약, 오늘의 프로그램 목록 갱신은 플레이어에게 하나의 행동이다. 저장 중간에 다른 시스템이 알림을 받고 같은 요청을 다시 보내도 “Gold만 줄었거나 예약만 남은 상태”를 볼 수 없게 해 달라는 요청이다.

**왜 필요한가**  
보통 클릭에서는 문제없어도 성공 알림을 처리하는 도중 같은 구매 요청이 다시 들어오면 이중 차감 또는 중간 상태 노출 위험이 있다.

**부탁할 작업**

1. 예약·Gold/원장·오늘 편성 목록을 모두 성공 상태로 만든 뒤 성공 알림을 한 번만 보내 주세요.
2. 중간에 하나라도 실패하면 모든 상태를 이전 값으로 되돌려 주세요.
3. 성공 알림 안에서 곧바로 같은 구매를 다시 요청하는 경우를 테스트해 주세요.

**완료 확인**

- [ ] 성공 1회에 Gold·예약·편성이 각각 정확히 한 번만 변경된다.
- [ ] 실패를 강제로 만들면 Gold·원장·예약·편성 목록이 모두 이전과 같다.
- [ ] 성공 알림을 받는 시점에는 네 상태가 모두 최종값이다.
- [ ] 같은 요청이 성공 알림 안에서 다시 들어와도 Gold가 두 번 빠지거나 주인 없는 예약이 남지 않는다.

**개발자 참고 위치**

- `FF_FestivalProgressionSubsystem.cpp`의 `TryScheduleProgram`
- `FF_ProgramReservationSubsystem.cpp`

### 요청 3 — 예약 저장소에서도 시간 겹침을 마지막으로 차단

**쉽게 말하면**  
새 시설 화면은 같은 시설의 시간이 겹치는 프로그램을 이미 막는다. 그래도 다른 화면이나 미래 코드가 예약 저장소를 직접 부를 수 있으므로 저장 직전에도 한 번 더 막아 달라는 요청이다.

**부탁할 작업**

- 같은 시설에서 시간이 실제로 겹치면 등록을 거절해 주세요.
- 한 프로그램이 끝나는 시각과 다음 프로그램이 시작하는 시각이 같으면 허용해 주세요.
- 다른 시설끼리는 시간이 같아도 허용해 주세요.
- 시설별 예약 목록이 필요하면 시작 시각 순으로 일정하게 반환해 주세요.

**완료 확인**

- [ ] 같은 시설의 `60~120분`과 `90~150분`은 실패한다.
- [ ] 같은 시설의 `60~120분`과 `120~180분`은 성공한다.
- [ ] 서로 다른 시설의 겹치는 시간은 성공한다.
- [ ] 새 구매 창구와 예약 저장소 직접 호출 양쪽에서 같은 결과가 나온다.

**개발자 참고 위치**

- `FF_ProgramReservationSubsystem.h/.cpp`의 등록 경계

### 요청 4 — 기획 데이터 검사를 Validate Assets에 연결

**쉽게 말하면**  
프로그램 가격이나 시간을 잘못 입력했을 때 기획자가 Content Browser의 **Validate Assets**만 눌러도 오류를 볼 수 있게 해 달라는 요청이다.

**현재 준비된 것**  
`UFF_ProgramAuthoringValidationLibrary::ValidateProgramCatalog`가 ID, 이름, 양수 값, 시간, 시설 타입 형식을 검사한다. 담당 파일을 건드리지 않기 위해 자동 메뉴 연결만 하지 않았다.

**부탁할 작업**

1. `FestivalDefinition`의 기존 `IsDataValid`에서 위 검증 함수를 호출해 주세요.
2. 오류마다 어떤 프로그램의 어떤 값인지 기획자가 읽을 수 있게 표시해 주세요.
3. `ProgramCatalog` 배열 항목 제목, 한글 설명, 카테고리를 기획자가 찾기 쉽게 다듬어 주세요.
4. 허용 시설 목록이 비면 “전 시설 허용”이라는 현재 정책을 유지할지 기획과 확정해 주세요.

**완료 확인**

- [ ] 빈/중복 ID, 빈 이름, 0 이하 값, 잘못된 시간, 잘못된 시설 형식을 Validate Assets가 거절한다.
- [ ] 오류에 프로그램과 필드 이름이 표시된다.
- [ ] 정상 카탈로그는 통과한다.
- [ ] 빈 허용 시설 목록이 기획에서 확정한 정책대로 동작한다.

**개발자 참고 위치**

- `FF_FestivalDefinition.h/.cpp`
- `FF_FestivalEconomyTypes.h`
- 신규 `FF_ProgramAuthoringValidationLibrary.h/.cpp`

## 4. 백종태님께 요청할 내용

### 요청 1 — 기존 Program 탭도 같은 구매 안전 규칙 사용

**쉽게 말하면**  
시설을 눌러 들어오는 새 화면은 강화된 안전 검사를 사용한다. 기존 PrepHUD의 Program 탭에서도 구매할 수 있으므로, 그 화면도 같은 문을 통과하게 해 달라는 요청이다.

**왜 필요한가**  
같은 프로그램인데 어느 화면에서 눌렀는지에 따라 시설 상태나 시간 충돌 검사 결과가 달라지는 일을 막는다.

**부탁할 작업**

1. ViewModel의 “구매 가능?” 조회를 `CanScheduleProgramAtFacility`로 바꿔 주세요.
2. 실제 확정은 `TryScheduleProgramAtFacility`만 호출해 주세요.
3. 버튼을 미리 비활성화해도 최종 클릭 시 다시 검사해 주세요.
4. 결과별 한글 실패 문구를 화면에 연결하고, 알 수 없는 결과를 성공으로 취급하지 말아 주세요.
5. 실제 성공 응답 전에는 성공으로 표시하지 말고, 실패 뒤 실제 상태를 다시 읽어 주세요.

**완료 확인**

- [ ] 시설 피커와 기존 Program 탭에서 같은 카드·시설은 같은 결과와 이유를 낸다.
- [ ] Setup/MorningCheck 외 단계, 사라진 시설, 잘못된 시설 타입, 재배치 시설, 시간 충돌에서 상태가 바뀌지 않는다.
- [ ] 실패 전에 성공 화면을 먼저 보여 주지 않고, 실패 후 실제 상태로 다시 그린다.
- [ ] 실제 UI 경로에 `Progression->TryScheduleProgram` 직접 호출이 남지 않는다.

**개발자 참고 위치**

- `FF_FestivalViewModelSubsystem.cpp`
- `FF_PrepPanelProgram.cpp`
- 신규 `FF_ProgramSchedulingSubsystem.h/.cpp`

### 요청 2 — 두 프로그램 화면을 합칠지는 선택 사항

현재는 팀원 파일을 건드리지 않기 위해 시설 전용 `WBP_FF_FacilityPaidProgramPicker`가 독립적으로 열린다. 팀에서 Program 화면 하나만 운영하고 싶다면 다음 사용 경험을 유지하면서 기존 탭에 흡수해 주세요.

- 시설 화면에서 들어오면 해당 시설은 고정되고 다른 시설로 바꿀 수 없다.
- 그 시설과 맞지 않는 카드는 고를 수 없다.
- 카드 한 번 클릭은 미리보기이며 결제가 아니다.
- 별도의 최종 **N Gold로 구매·편성** 버튼이 있어야 한다.
- 취소하면 아무 상태도 바뀌지 않는다.
- 성공 뒤 시설 정보와 프로그램 목록을 실제 상태로 다시 읽는다.

두 진입 경로가 모든 완료 확인 항목에서 같은 결과를 내고 QA를 통과한 뒤에만 독립 피커 제거 여부를 결정해 주세요.

## 6. 용어를 모르는 사람을 위한 설명

| 용어 | 뜻 |
|---|---|
| WBP / UMG | 언리얼에서 버튼, 글자, 화면 배치를 만드는 UI 에셋 |
| DataAsset | 기획자가 코드 수정 없이 숫자와 목록을 저장하는 데이터 파일 |
| Subsystem | 특정 기능과 규칙을 한곳에서 맡는 관리자 코드 |
| 시설 고유 번호 | 월드에 설치된 시설 한 개를 정확히 구별하는 값. 코드에서는 `FacilityInstanceId` 또는 GUID |
| 사전 판정 | 버튼을 누르기 전에 가능 여부와 이유를 보여 주는 검사 |
| 최종 검사 | 결제 순간 바뀐 값까지 다시 확인하는 검사 |
| 원자성 | 여러 저장을 한 행동처럼 모두 성공하거나 모두 취소하는 성질 |
| 재진입 | 성공 알림을 처리하는 도중 같은 기능이 다시 호출되는 상황 |
| 이벤트/델리게이트 | 한 시스템의 변경 사실을 다른 시스템에 즉시 알리는 신호 |
| 시간 경계 규칙 | 10~11시 다음에 11~12시는 가능하지만 10~12시와 11~13시는 불가한 규칙 |

## 7. 공통 완료 확인과 통합 순서

1. 각 담당자가 위 요청 중 자신의 영역을 검토한다.
2. 참가비 확정 시점과 빈 허용 시설 목록 정책은 코드보다 먼저 기획과 합의한다.
3. 담당 브랜치에서 구현하고 담당 영역 테스트를 진행한다.
4. 에디터 빌드/UHT가 통과하는지 확인한다.
5. `FF.BuildFacilityInfoUMG`를 두 번 실행해 두 번째가 `REUSE`이고 기존 디자이너 스타일이 유지되는지 확인한다.
6. 편성 시설의 Move/Remove는 거절되고 미편성 시설은 허용되는지 확인한다.
7. 통합 브랜치에서 **시설 클릭 → 카드 미리보기 → 구매·편성 → Live 참가 → 다음 날 초기화**를 함께 확인한다.
8. 다른 사람 소유 파일을 추가로 바꿔야 하면 변경 이유, 필요한 API, 완료 조건을 먼저 공유한다.
