# FestaFiesta Development 빌드 — NPC 출현 점검 안내

기준: 2026-09-11 / Windows 64비트 / Unreal Engine 5.7.4.

이 문서는 콘솔과 실행 로그를 사용할 수 있는 **Development 테스트 빌드**용이다. 패키지에서는 이 문서가 `README_KO.md`로 제공된다. 빌드 이름은 동봉된 `build-manifest.json`에서 확인한다. 이 문서의 제작 명령은 `FestaFiesta-Win64-Development-SingleExe-20260911` 라벨을 사용한다.

## 이번에 확인하는 문제

일부 실행에서 축제가 Live 단계에 들어가도 NPC가 나오지 않는 현상의 원인으로 **사용 중인 입장 시간표와 외형 표의 메모리 수명 문제**를 재현해 수정했다. 초기화 때 표를 읽었더라도, 이후 엔진이 사용하지 않는 메모리를 정리하면 표가 사라져 입장 처리가 멈출 수 있는 구조였다.

행사장 직원에게 입장 시간표를 건네주었는데, 창고를 정리하는 사람이 그 종이를 사용하지 않는 자료로 판단해 치워 버리는 상황에 비유할 수 있다. 수정은 실행 중 필요한 시간표와 관련 데이터를 계속 보관하도록 만드는 것이다. 엔진의 자동 메모리 정리는 사용하는 상태에서 검증한다.

이 문서는 실행·재현·판독 방법을 설명한다. 빌드별 자동 검사 수치와 최종 결과는 별도 검증 보고서에서 확인한다. 테스트 PC에서의 실제 화면, 다음 날, 로비 재입장 결과는 아래 절차로 확인하고 해당 실행 로그와 함께 기록한다.

## 1. 압축을 풀고 테스트 실행하기

1. ZIP 전체를 쓰기 가능한 폴더에 압축 해제한다. 예: `C:\Games\FestaFiesta-NpcTest`. 실행 파일만 따로 옮기지 않는다.
2. 처음 실행하는 PC라면 동봉된 `Engine\Extras\Redist\en-us\vc_redist.x64.exe`를 실행해 필수 구성 요소를 설치한다.
3. 압축을 푼 **맨 위 폴더의 `FestaFiesta.exe` 하나를 더블클릭**한다. 일반 실행에 명령어 입력이나 그래픽 모드 선택은 필요하지 않다.

게임은 시작할 때 기본 DirectX 12 / Shader Model 6 지원 여부를 확인한다. 이 경로가 지원되지 않으면, 지원되는 환경에서 DirectX 11 / Shader Model 5 경로를 선택한다. 그래픽 장치를 만든 뒤 발생하는 드라이버 오류나 플레이 중 비정상 종료까지 자동 복구하는 기능은 아니다.

**사용자가 누르는 시작 파일은 하나지만, 게임 데이터 폴더도 함께 필요하다.** `FestaFiesta.exe`는 극장의 입구, `FestaFiesta`와 `Engine` 폴더는 무대·배우·조명 장비라고 생각하면 된다. 입구만 옮기면 공연할 수 없다. `FestaFiesta`, `Engine`, `Licenses`와 동봉 문서를 같은 위치에 보관하고, 하위 폴더의 실행 파일이나 DLL을 정리 대상으로 지우지 않는다.

일반 Development 실행 로그는 게임 폴더의 `FestaFiesta\Saved\Logs\FestaFiesta.log`에 기록된다. 별도 로그 창을 여는 실행 옵션은 필요하지 않다. 이 문서의 뒤쪽에 있는 고급 그래픽 QA를 제외하면 계속 같은 `FestaFiesta.exe`로 실행한다.

## 2. 정상적인 게임 흐름으로 Live까지 진행하기

1. 로비에서 새 게임을 시작한다.
2. Setup에서 게임이 안내하는 필수 시설을 설치하고 준비 과정을 마친다.
3. 게임 화면의 정상적인 진행 버튼으로 Live에 진입한다. 준비 조건이 부족하다는 안내가 나오면 해당 조건을 충족한다.
4. Live에 들어갔는지 화면을 확인하고 게임 내 시계가 실제로 진행되는지 본다. 일시 정지는 해제한다.
5. 수초 동안 관람객 입구 주변을 확인한다. 이어서 아래 콘솔 명령으로 숫자를 비교한다.

**Setup이나 MorningCheck에서 아직 NPC가 0명인 것은 정상일 수 있다.** 이 프로젝트는 Live 진행도에 따라 나누어 입장시키므로, Live로 전환되는 바로 그 순간에 전원이 나타날 필요도 없다.

현재 맵의 저작 설정은 요청 인원 500명, 화면 표시 Actor 풀 500개, 논리 Agent 풀 500개다（10/14 기준 코드 기본값은 하루 기본 방문객 1,000명(하루 누적, 동시 인원은 그보다 적음)·스폰 Actor/Agent 풀 1,100개로 바뀌었다. 맵에 놓인 인스턴스 값은 에디터에서 확인한다）. 인원은 동행 그룹 단위로 구성되므로 실제 계획 인원이 요청보다 조금 작을 수 있다. 이 숫자는 설정값이며, 최종 실행에서 실제로 나온 인원은 로그로 확인한다.

길 없이 시설을 설치할 수 있는 규칙과 관람객이 그 시설까지 걸어갈 수 있는지는 별개다. NPC가 생성되었지만 특정 시설에 도착하지 못하는 현상은 출현 여부 다음 단계에서 확인한다.

## 3. 콘솔 열고 읽기 전용 진단하기

게임 창을 클릭해 입력 초점을 준다. 키보드를 영문 입력 상태로 바꾸고 숫자 `1` 왼쪽의 **물결표/백틱 키(`~`/`` ` ``)**를 눌러 콘솔을 연다. 아래 명령을 한 줄씩 입력하고 Enter를 누른다. 다시 같은 키를 눌러 콘솔을 닫을 수 있다.

```text
FF.Crowd.Arrival
FF.Crowd.Stats
FF.Crowd.StageFlow
```

이 세 명령은 현재 상태를 읽는다. NPC를 강제로 만들거나 축제 단계를 바꾸지 않는다. 특히 `FF.Crowd.Arrival`은 실행 중인 시간표 캐시를 읽으며, 진단하는 동안 표를 새로 불러와 증상을 가리지 않는다.

콘솔이 열리지 않으면 `build-manifest.json`의 `target.configuration`이 `Development`인지 확인하고, 게임 창에 초점을 준 뒤 영문 입력 상태에서 다시 시도한다. 일반 `FestaFiesta.exe` 더블클릭 실행에서도 콘솔을 사용할 수 있다. 기존 Shipping 배포본에서는 같은 진단 기능을 사용할 수 없다.

### FF.Crowd.Arrival — 입장 명단과 시계

“현재 몇 명까지 들어왔어야 하고, 실제로 몇 명을 입장시켰는가”를 확인한다. 요약 줄의 뜻은 다음과 같다.

| 항목 | 뜻 | 확인 방법 |
| --- | --- | --- |
| `Stage` | 현재 축제 단계 | Live에서 출현 문제를 검사 중인지 확인 |
| `TableLoaded` | 실행 중인 입장 시간표가 메모리에 있는지 | Live 입장 처리 중에는 사용 가능한 상태여야 함 |
| `Planned` | 이번 입장 일정의 계획 인원 | 0이면 계획 자체가 비었는지 조사 |
| `Admitted` / 입장 누적 | 이번 일정에서 지금까지 입장시킨 인원 | Live 초반·중반에 시간을 두고 증가하는지 비교 |
| `Active` | 현재 시뮬레이션 중인 인원 | 이미 퇴장한 인원은 제외되므로 누적과 다를 수 있음 |
| `Bound` | 실제 화면용 캐릭터와 연결된 인원 | 논리 인원은 있는데 화면에 안 보이는 문제를 구분 |
| Live 경과 / 진행도 | 입장 계산에 사용하는 시계 | 콘솔을 닫고 기다린 뒤 다시 조회하여 증가 확인 |

콘솔을 닫고 **5~10초 정도 실제 게임을 진행한 뒤** 다시 `FF.Crowd.Arrival`을 입력한다. Live가 아직 진행 중이고 입장 계획이 남았다면, 시계와 누적 입장이 계속 진행되는지 본다. 종료 시점이나 Closing에서는 신규 입장이 멈추는 것이 정상이다.

### FF.Crowd.Stats — 만들어진 사람과 보이는 사람

`활성 Agent`는 숫자로 시뮬레이션하는 관람객, `화면 표시 Actor`는 화면용 캐릭터와 연결된 관람객이다. 명부에 적힌 사람 수와 실제로 배정된 캐릭터 수를 비교한다고 생각하면 된다.

- 두 숫자 모두 0이면 입장 일정·단계·시간표를 먼저 본다.
- 활성 Agent는 있는데 화면 표시 Actor가 0이면 캐릭터 연결·표시 문제를 조사한다.
- 두 숫자가 모두 양수인데 특정 장소에 사람이 없으면 실제 입구 위치와 이동 목적지를 확인한다. 연결된 Actor 수가 양수라는 사실만으로 현재 카메라 안에 보인다는 뜻은 아니다.
- `쿼리 / 실패`, `부분 경로`, `경로 대기`는 생성 후 이동 경로 상태를 판단하는 자료다.

### FF.Crowd.StageFlow — 어디로 가려는지

현재 단계, 지역별 파티, 시설 후보, 대기열, 내비게이션 상태를 출력한다. 인자를 생략하면 첫 번째 유효한 활성 파티 리더를 골라 설명한다.

아직 사람이 없어서 `No valid active leader`가 나오는 것은 이 명령이 분석할 파티가 없다는 뜻이다. 그 메시지만으로 별도 고장이라고 판단하지 말고 Arrival과 Stats를 먼저 확인한다.

특정 리더를 분석할 때는 출력에 나온 **leader agent index**를 사용한다. 예를 들어 실제 출력에서 리더 인덱스가 12였다면 다음처럼 입력한다. `PartyId`와 다른 숫자다.

```text
FF.Crowd.StageFlow 12
```

## 4. 메모리 정리 뒤에도 입장이 계속되는지 확인하기

기본 재현은 Setup에서 준비 작업을 충분히 진행한 다음 정상적으로 Live에 들어가 확인하는 것이다. 빨리 시작한 실행과 한동안 준비한 실행을 비교한다.

Development에서 메모리 정리를 직접 발생시키는 추가 검사도 가능하다. 아래 명령은 앞의 읽기 명령들과 달리 **엔진 메모리 정리를 한 번 실행**한다. NPC 생성이나 단계 전환을 강제로 수행하지는 않는다.

```text
obj gc
```

1. 새 게임의 Setup에서 `obj gc`를 한 번 실행한다.
2. 정상적인 준비 조건을 충족해 Live로 진행한다.
3. `FF.Crowd.Arrival`에서 시간표가 남아 있고, 시계가 진행되며, 입장 수가 증가하는지 확인한다.
4. 입장 계획이 남아 있는 Live 초반에 `obj gc`를 한 번 더 실행한다.
5. 콘솔을 닫고 5~10초 진행한 뒤 Arrival과 Stats를 다시 확인한다. 정리 전후의 로그를 함께 보관한다.

엔진은 정리 중 잠시 멈출 수 있다. 확인할 것은 그 짧은 정지 자체가 아니라, 이후 정상적으로 시간이 흐를 때 입장 처리가 계속되는지다. 초기 입장 수가 잠깐 0이었던 장면만으로 결론 내리지 않는다.

## 5. 다음 날과 로비 재입장도 확인하기

| 상황 | 수행할 작업 | 확인할 결과 |
| --- | --- | --- |
| 첫날 시작 | 로비 → 새 게임 → 준비 → Live | 시계 진행, 신규 입장, 실제 캐릭터 표시 |
| 다음 날 | 게임의 마감·결산·다음 날 흐름을 거쳐 MorningCheck → Live | 새 입장 일정이 시작되고 NPC가 다시 나타남 |
| 로비 재입장 | 게임 메뉴로 로비 복귀 → 새 게임 → 준비 → Live | 이전 월드의 상태에 막히지 않고 새 월드에서 생성 |
| 메모리 정리 | Setup 및 Live 중 `obj gc` 후 정상 진행 | 사용 중인 시간표가 유지되고 입장이 계속됨 |
| 재실행 | 게임 종료 → 맨 위 `FestaFiesta.exe` 더블클릭 → 같은 과정 | 일반 시작 경로에서 NPC가 다시 나타남 |

각 날짜의 누적 입장 수는 새 일정 기준으로 비교한다. 이전 날짜에서 이어서 무조건 증가해야 하는 숫자는 아니다. 화면상 현재 인원은 퇴장에 따라 줄어들 수 있다.

## 6. 문제가 남으면 기록할 내용

재현 직후 Arrival, Stats, StageFlow를 차례로 실행하고 정상 종료한다. 게임 폴더의 `FestaFiesta\Saved\Logs`에서 수정 시간이 가장 최근인 로그를 찾는다. 다음 내용을 함께 전달하면 원인을 좁힐 수 있다.

```text
빌드 이름 / build-manifest.json:
실행 방법: 맨 위 FestaFiesta.exe 더블클릭 (고급 QA였다면 지정한 옵션)
Windows / GPU / 드라이버:
새 게임인지, 다음 날인지, 로비에서 재입장했는지:
현재 단계 / 날짜:
Live 진입 후 기다린 시간:
TableLoaded / Planned / Admitted / Active / Bound:
메모리 정리 실행 여부와 시점:
보이는 증상과 재현 순서:
첨부한 FestaFiesta\Saved\Logs 파일 이름:
```

| 관찰 | 우선 조사할 부분 |
| --- | --- |
| Live인데 시계가 늘지 않음 | 시간 진행·일시 정지·축제 상태 |
| Live 시계는 늘고 계획도 있는데 `TableLoaded`가 꺼짐 | 시간표의 로딩·메모리 수명 |
| 시간표와 시계는 정상인데 누적 입장이 늘지 않음 | 입장 목표·방문객 명단·Agent 풀 |
| 활성 인원은 증가하지만 표시 Actor가 0 | 캐릭터 풀과 연결·표시 |
| NPC는 있으나 시설에 도착하지 못함 | 시설 접근점·대기열·NavMesh 경로 |

이 표는 로그를 분류하는 출발점이다. 한 숫자만 보고 설정을 임의로 바꾸기보다 재현 시점의 전체 로그와 함께 판단한다.

## 7. 담당자용 고급 검사 — 그래픽 경로를 각각 지정하기

일반 사용자는 1장의 더블클릭 실행을 사용한다. 두 그래픽 경로를 따로 검증하는 담당자만 게임을 종료한 뒤, `FestaFiesta.exe`가 있는 맨 위 폴더에서 PowerShell을 열고 아래 명령을 **한 번에 하나씩** 실행한다. 각 실행을 정상 종료하고 다음 명령을 사용한다.

```powershell
# DirectX 11 / Shader Model 5 경로
.\FestaFiesta.exe -dx11 -sm5 -windowed -ResX=1600 -ResY=900

# DirectX 12 / Shader Model 6 경로
.\FestaFiesta.exe -dx12 -sm6 -windowed -ResX=1600 -ResY=900
```

두 모드에서 2~5장의 정상 게임 흐름을 같은 조건으로 반복하고 실제 화면과 NPC, 다음 날, 로비 재입장을 기록한다. `-dx12 -sm6`와 같은 강제 옵션은 해당 경로의 지원을 요구하므로, 일반 실행의 자동 선택과 다른 검사다. 두 경로를 같은 GPU에서 확인한 결과만으로 모든 구형 GPU의 호환성을 보장하지 않는다.

각 모드 종료 직후 `FestaFiesta\Saved\Logs`의 해당 실행 로그를 배포 폴더 밖에 복사해 모드 이름과 함께 보관한다. 이어서 **옵션 없이 `FestaFiesta.exe`를 더블클릭하는 일반 실행**도 확인한다.

## 8. 소스 프로젝트에서 같은 Development 패키지 만들기

이미 프로젝트를 받아 개발 환경을 준비한 담당자를 위한 명령이다. 엔진은 UE **5.7.4**, Windows SDK와 MSVC는 저장소의 `Tools/Build/toolchain.lock.json`에 고정된 버전을 사용한다. C++ 빌드 도구, Git LFS 파일과 충분한 디스크 공간이 준비되어 있어야 한다.

PowerShell에서 프로젝트 폴더로 이동한 뒤 실행한다. 프로젝트 위치와 엔진 설치 위치가 다르면 해당 경로를 바꾼다.

```powershell
Set-Location 'C:\GitHub\FestaTeam\8th-Team13-Final-Project'

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Tools\Build\Package-Win64.ps1 `
  -EngineRoot 'C:\Program Files\Epic Games\UE_5.7' `
  -Configuration Development `
  -BuildLabel 'FestaFiesta-Win64-Development-SingleExe-20260911' `
  -GraphicsSmokeTest
```

**`-Configuration Development`를 반드시 적는다.** 생략하면 기본값인 Shipping을 만든다. `-GraphicsSmokeTest`는 같은 패키지의 DX11/SM5와 DX12/SM6 초기화를 추가 검사한다. 실제 NPC·맵 플레이 확인은 이 문서의 수동 절차로 이어서 수행한다.

정규 명령은 자동화와 콘텐츠 검증을 수행한다. 실패한 경우 출력 로그를 확인해 원인을 해결한 뒤 다시 실행한다. 기존 결과를 덮어쓰지 않으므로 같은 빌드 이름이 이미 있으면 새 이름을 사용한다. 예: `FestaFiesta-Win64-Development-SingleExe-20260911-R2`.

완료된 결과는 기본적으로 `Artifacts\Releases\<빌드 이름>`에 생긴다. 해당 폴더의 ZIP은 공유용 전체 패키지이며, `Validation`은 자동화·콘텐츠 검사, `Logs`는 패키징 기록, `Metadata`는 검사 결과와 파일 무결성 자료다. 실패한 작업은 `.staging` 아래 기록을 확인하고, 오류가 난 임시 결과를 완료된 배포본으로 전달하지 않는다.

사용자가 일반 실행으로 플레이한 Development 게임 로그는 **압축을 푼 게임 폴더의 `FestaFiesta\Saved\Logs`**에서 찾는다. 빌드하는 과정의 `Logs` 및 자동 검사의 별도 출력 폴더와 구분한다. 플레이한 복사본에는 사용자 설정과 로그가 추가될 수 있으므로 공유용 ZIP은 패키징 결과의 원본을 사용한다.
